## ۱. خلاصه مدیریتی

پروژه از نصب اولیه Nuxt و رفع مشکلات ابزارها به ساخت رابط صفحه اصلی و صفحات مستقل رسیده است. برای صفحه اصلی، ده بخش طراحی و کدنویسی شده و لاگ کامیت‌های کاربر ایجاد آن‌ها را تأیید می‌کند. کد صفحات مقالات، جزئیات مقاله، درباره، خدمات، حریم خصوصی و خطا نیز در گفت‌وگو ارائه شده است؛ برای این صفحات شواهد بیلد یا کامیت در اختیار نداریم.

بک‌اند طبق اعلام کاربر آماده نیست. جهت فعلی کار، تکمیل فرانت‌اند، انتقال داده‌های ثابت به فایل‌های مشترک و استفاده از Nuxt Content برای مقالات است. راه‌اندازی Nuxt Content هنوز انجام‌شده گزارش نشده است.

آخرین درخواست اجرایی کاربر، بازنویسی کامل و نهایی کامپوننت‌ها به‌صورت فایل‌به‌فایل است. فایل‌های `AppHeader.vue` و `AppFooter.vue` ارسال و خوانده شدند، اما نسخه کامل بازنویسی‌شده آن‌ها هنوز تحویل نشده است. این نقطه مناسب ادامه کار است.

نسخه اولیه تابع ارسال، پس از تأخیر مصنوعی پیام موفقیت نشان می‌داد و فرم را پاک می‌کرد. این رفتار اشکال دارد: هیچ داده‌ای ثبت نمی‌شود. اصلاح بعدی پیشنهاد شد که فقط پیام غیرفعال‌بودن ارسال را نشان دهد و داده‌ها را نگه دارد. اجرای این اصلاح توسط کاربر تأیید نشده است.

پیام در سند اولیه اختیاری بود ولی در کد فرم required شد؛ این ناسازگاری نیز باید اصلاح شود. اعتبارسنجی واقعی شماره، خطاهای کنار فیلد و حالت‌های ارسال به API هنوز تکمیل نیستند.

### اولویت بالا

1. حذف موفقیت ساختگی و پاک‌کردن داده در فرم بدون بک‌اند.
2. در کدهای اولیه مقاله، عددهای `۶`، `۵` و `۴` به‌صورت مقدار بدون نقل‌قول نوشته شدند؛ باید در JavaScript عددهای `6`، `5` و `4` باشند و فارسی‌سازی در نمایش انجام شود.
3. بررسی محل error.vue با تنظیمات واقعی Nuxt 4.
4. جلوگیری از تودرتو شدن main: Layout یک main دارد؛ صفحات نمونه مستقل نیز main دارند. ریشه صفحات باید مثلاً div باشد و main اصلی در Layout بماند.
5. بررسی import یا نام خودکار AppHeader و AppFooter در مسیر components/layouts؛ اتکا به نام کوتاه بدون تنظیم یا import می‌تواند مشکل‌ساز شود.
6. تکمیل نسخه کامل دو فایل ارسالی هدر و فوتر، مطابق درخواست بی‌پاسخ کاربر.

### اولویت متوسط

- تشخیص لینک فعال: startsWith ساده می‌تواند مسیر نامرتبط را فعال کند؛ مسیر و hash باید جدا بررسی شوند. hash در SSR نیز نیازمند توجه است.
- افزودن توضیح دسترس‌پذیر برای Sheet و بررسی بستن منو، فوکوس و اسکرول در موبایل.
- مدیریت خطای navigator.share، لغو کاربر و عدم دسترسی clipboard؛ نمایش بازخورد کپی.
- در جزئیات مقاله، بررسی کلیدهای نامعتبر و واکنش به تغییر slug در ناوبری داخلی.
- حذف تلفن، ایمیل، آدرس و لینک اجتماعی نمونه از هدر/فوتر/تماس و نمایش شرطی اطلاعات واقعی.
- هماهنگ‌سازی خدمات صفحه اصلی و صفحه مستقل از یک منبع.
- تعویض متن «اطلاعات بیشتر» در لینک‌هایی که صرفاً به فرم تماس می‌روند.
- بررسی تم تیره در کدهای دارای bg-white و text-primary-900 ثابت.
- کنترل حداقل اندازه متن، کنتراست، فوکوس و کاهش حرکت.
- عدم نمایش نظرات ساختگی، مدارک نامشخص، آمار بی‌منبع و وعده‌های قطعی.

### وضعیت کیفیت

خروجی ثبت‌شده‌ای از build، typecheck، آزمون مرورگر یا آزمون دسترس‌پذیری نهایی در دست نیست. موفقیت nuxt prepare فقط تولید فایل‌های Nuxt را تأیید می‌کند، نه سلامت کامل برنامه.

## ۱۲. برنامه ادامه کار

### مرحله اول — نهایی‌سازی اجزای ارسالی

- تحویل کامل AppHeader.vue و AppFooter.vue با data مشترک.
- حفظ طراحی موجود و اصلاح لینک فعال، منوی موبایل و اطلاعات شرطی.
- مشخص‌کردن وابستگی به site.ts و navigation.ts.
- اجرای بیلد توسط توسعه‌دهنده و رفع خطاهای واقعی.

### مرحله دوم — تکمیل مهاجرت داده

- بازنویسی ServicesSection و services.vue با منبع مشترک.
- انتقال FAQ به فایل مشترک.
- استفاده از site در Hero، فرم، متادیتا و صفحات معرفی.
- حذف نام‌ها و اطلاعات تکراری بدون تغییر ناخواسته در متن.

### مرحله سوم — Nuxt Content

- راه‌اندازی مجموعه مقالات و schema.
- انتقال سه نمونه به Markdown با وضعیت پیش‌نویس روشن.
- اتصال هر سه محل نمایش مقاله به منبع واحد.
- کنترل مسیر نامعتبر، حالت بدون مقاله، متن و متادیتا.

### مرحله چهارم — یکپارچگی رابط

- اصلاح main، error.vue، importها و ارقام JavaScript.
- بررسی هدر و فوتر در تمام صفحات.
- بررسی عرض‌های موبایل، تبلت و دسکتاپ.
- کنترل anchorها، فوکوس، منوی موبایل و فرم نمایشی.

### مرحله پنجم — آماده‌سازی انتشار

- دریافت اطلاعات واقعی برند، روان‌شناس، خدمات و راه‌های تماس.
- بازبینی محتوای تخصصی و سیاست حریم خصوصی.
- اتصال فرم فقط بعد از آماده‌شدن بک‌اند و تعریف قرارداد API.
- تست حالت موفقیت واقعی، شکست، انتظار و جلوگیری از ارسال تکراری.
- انتخاب محیط استقرار، بیلد نهایی و بررسی صفحات منتشرشده.

## ۱۴. دستورهای پیشنهادی برای ثبت وضعیت واقعی

از ریشه مخزن:

```bash
git status

git log origin/main..HEAD --oneline
```

از پوشه frontend:

```bash
bun run build
```

اسکریپت بررسی نوع‌ها باید از package.json فعلی بررسی و سپس اجرا شود؛ وجود اسکریپت typecheck فرض نشده است. خروجی این دستورها باید مبنای گزارش بعدی قرار گیرد.
